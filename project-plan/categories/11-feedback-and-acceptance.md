# 11. Обратная связь и критерии готовности / Feedback and acceptance criteria

Этот список собирает правки, переданные командой 8 октября 2026 года. Он задаёт порядок исправления прототипа и критерии, по которым можно принять работу. Планы, проверки кода, сборка и ручная проверка на Mac считаются разными уровнями готовности.

This list records the team's feedback received on 8 October 2026. It sets the prototype-fix order and acceptance criteria. Plans, code checks, builds, and hands-on Mac review count as separate levels of readiness.

## Уточнение по предмету «Биология» / Clarification about Biology

**RU:** Последняя поправка команды отменяет прежнюю трактовку, будто нужно создавать биологию заново или добавлять её как новый встроенный предмет. Биология уже входит в стандартный каталог. Требование — дать ученику возможность самому создать новый предмет и добавлять темы и подтемы как в пользовательские, так и в существующие предметы. Общая проверка навигации по встроенным урокам остаётся нужна, но отдельный дефект открытия биологии не считать подтверждённым без воспроизведения.

**EN:** The team's latest clarification supersedes the earlier interpretation that Biology should be created again or added as a new built-in subject. Biology is already in the standard catalog. The requirement is to let learners create new subjects and add topics and subtopics to both custom and existing subjects. General navigation checks for built-in lessons still apply, but do not treat a Biology-specific opening bug as confirmed unless it is reproduced.

## Уточнение о продуктовом промпте / Clarification about the product prompt

**RU:** Большой промпт из командной записи — техническое задание на проектирование и разработку самого образовательного приложения: его интерфейса, архитектуры, учебных маршрутов, персонализации, источников, визуализаций и проверяемых переходов. Это не системная инструкция для отдельного AI-тьютора. Тьютор — один из компонентов продукта. Новые элементы добавлять поэтапно, исходя из пользы для обучения; сначала исправлять P0, а не выдавать запланированные функции за готовые.

**EN:** The long prompt in the team transcript is a specification for designing and building the educational application itself: its interface, architecture, learning paths, personalization, sources, visualizations, and verifiable navigation. It is not a system prompt for a standalone AI tutor. The tutor is one component of the product. Add further elements incrementally according to their learning value; fix P0 failures first and do not present planned features as complete.

## Пользовательская программа и визуальное покрытие / Learner curriculum and visual coverage

**RU:** Приёмка должна подтвердить, что ученик может создать собственный предмет и дерево тем/подтем, а также добавить тему во встроенный предмет, включая биологию. Сейчас прототип сохраняет двуязычную структуру, цели, заметки и локальный прогресс; в чате темы есть заранее заполненный запрос на черновик плана. Ответ пока не разбирается в сохраняемые подтемы. Следующая приёмка должна проверить, что ИИ предлагает структуру по заметкам, ученик может её просмотреть и поправить до сохранения, а непроверенные факты остаются помеченными.

**EN:** Acceptance must confirm that a learner can create a custom subject and a tree of topics/subtopics, and add a topic to a built-in subject, including Biology. The prototype currently saves bilingual structure, goals, notes, and local progress; topic chat has a prefilled request for a study-plan draft. The reply is not yet parsed into saved subtopics. Next acceptance must verify that AI proposes a structure from learner notes, the learner can review and edit it before saving, and unverified claims remain labelled.

**RU:** Вести покрытие визуализациями отдельно по предметам и темам. Большинство основных тем должно иметь работающую и полезную визуальную поддержку, выбранную по содержанию: 3D там, где нужно пространственное исследование, и график, схема, опыт, видео или другая интерактивность там, где они полезнее. Для каждого модуля проверять связь с учебной целью, источник и права, доступность, текстовую альтернативу, допущения и ограничения. Пустая карточка или статичная декорация не считается визуализацией.

**EN:** Track visualization coverage by subject and topic. Most core topics should have a working, useful visual aid chosen for the content: 3D when spatial inspection matters, and a graph, diagram, experiment, video, or other interaction when that is more useful. For each module, check its learning goal, source and rights, accessibility, text alternative, assumptions, and limits. An empty card or static decoration does not count as a visualization.

## Самооценка типа ошибки / Learner-reported error type

**RU:** После неправильного ответа ученик может по желанию отметить, что именно ему помешало: понимание, память, применение, внимание к условию, логика, базовые знания или выбор метода. Перед повторной попыткой приложение предлагает короткую стратегию для выбранного типа. Отметка сохраняется с локальным прогрессом и показывается как самооценка по последним проверкам; она не является автоматическим диагнозом и сама по себе не доказывает освоение темы. Пропуск доступен всегда. Следующий этап — связать накопленные сигналы с конкретными предпосылками и учебными заданиями, не делая выводов из одной ошибки.

**EN:** After a wrong answer, learners may optionally report what got in the way: understanding, memory, application, attention to the prompt, reasoning, prerequisite knowledge, or method choice. Before retrying, the app offers a short strategy for the selected category. The report is stored with local progress and shown as self-reported difficulty from recent checks; it is not an automated diagnosis and does not by itself prove mastery. Skipping is always allowed. The next step is to connect accumulated signals to explicit prerequisites and learning activities without drawing conclusions from one mistake.

**Статус внедрения / Implementation status — 2026-10-08:** после неправильного ответа добавлен необязательный выбор категории и двуязычная подсказка к повтору. Неудачная и успешная попытки сохраняются отдельными событиями с явным признаком результата; неудачная проверка не открывает следующий уровень. Категории ошибок агрегируются по истории попыток, проходят проверку, попадают в резервную копию и показываются на главном экране как число тем с такой самооценкой. GitHub Actions [37753036863](https://github.com/invinby/coli-dev/actions/runs/37753036863) прошёл backend suite, все Swift-verifier'ы и сборки с упаковкой для Apple Silicon и Intel. Ручной просмотр на Mac и реальный цикл «ошибка → повтор → отметка на главном экране» ещё нужно выполнить. Следующий шаг — проверить этот сценарий на Mac и затем связывать повторяющиеся самоотчёты с явными предпосылками и заданиями.

**Implementation status / Статус внедрения — 2026-10-08:** the optional error-category choice and bilingual retry strategy are now shown after a wrong answer. Failed and successful attempts are stored as separate events with an explicit outcome; a failed check cannot unlock the next level. Error categories are aggregated across attempts, validated, included in backups, and shown on the dashboard as a count of topics with that self-report. GitHub Actions [37753036863](https://github.com/invinby/coli-dev/actions/runs/37753036863) passed the backend suite, every Swift verifier, and packaged builds for Apple Silicon and Intel. A hands-on Mac review and the real “wrong answer → retry → dashboard” flow remain to be checked. Next, verify this flow on a Mac, then connect repeated self-reports to explicit prerequisites and practice activities.

### Рекомендация по повторяющейся самооценке / Recommendation from repeated self-reports

**RU:** Когда одна и та же категория самооценки указана минимум в двух проверках по теме, а последняя проверка знаний по этой теме явно не пройдена и содержит ту же отметку, главная может предложить повторить именно эту тему и показать соответствующую двуязычную стратегию. Более свежая успешно пройденная проверка снимает этот приоритет. Одной ошибки недостаточно; это учебная подсказка по выбору самого ученика, не диагноз. Обычное продолжение незавершённого урока и просроченные повторы сохраняют приоритет.

**EN:** When the same self-reported category appears in at least two checks for a topic, and the latest knowledge check for that topic is explicitly failed and carries the same report, the dashboard may recommend that topic with the matching bilingual review strategy. A later passed check removes this priority. One mistake is not enough; this is a study suggestion based on the learner's own report, not a diagnosis. Resuming an unfinished lesson and due reviews retain priority.

**Статус внедрения / Implementation status — 2026-10-08:** алгоритм и RU/EN-подсказка добавлены; Swift-verifier покрывает приоритет повторяющегося сигнала над общим числом повторов и снятие рекомендации после успешной проверки. GitHub Actions [37753036863](https://github.com/invinby/coli-dev/actions/runs/37753036863) прошёл backend-проверки и сборки macOS для Apple Silicon и Intel.

**Implementation status / Статус внедрения — 2026-10-08:** the selector and RU/EN guidance are implemented; the Swift verifier covers prioritizing a repeated report over a generic retry count and clearing that priority after a passed check. GitHub Actions [37753036863](https://github.com/invinby/coli-dev/actions/runs/37753036863) passed the backend checks and Apple Silicon and Intel macOS builds.

Проверять облако только при явно выбранной бесплатной политике; любые проверки, расходующие квоту, запускать только по действию пользователя с ясным предупреждением. / Check backend health, Ollama, and the cloud route separately, then send a minimal end-to-end tutor request through each route. Do not show “model response verified” until a model has replied. Probe cloud only under the explicitly selected free policy; run any check that consumes quota only after a clear user action and warning. |
| P0 — навигация | Ни один ожидаемый экран не должен заканчиваться состоянием вроде «материал не найден», если у предмета есть урок. Не создавать копии встроенных предметов для обхода проблем навигации. | No expected screen should end at “material not found” when a subject has a lesson. Do not duplicate built-in subjects to work around navigation problems. | Проверить переходы из каталога, дорожной карты, карточки урока и кнопки «Продолжить». | P1 — качество заданий | В случайном порядке показывать варианты ответа при каждой новой попытке; во время вопроса не менять соответствие варианта правильному ответу. Разбирать и верный, и неверный ответ. | Shuffle answer choices on each new attempt while keeping the answer mapping stable during the question. Explain both correct and incorrect answers. | Автоматически проверить корректность индекса, появление правильного варианта на разных позициях и сохранение результата после перемешивания. / Automatically verify the answer mapping, varied correct-answer positions, and correctness after shuffling. |
| P1 — достоверность | Указывать для учебного утверждения официальный или научный источник, дату проверки и область действия. Не выдумывать ссылки, исследования и свежесть. Спорные положения помечать. | Provide an official or scientific source, review date, and scope for sourced learning claims. Do not invent citations, studies, or freshness. Mark disputed claims. | Для каждого готового урока проверять рабочие ссылки, точность тезисов и лицензионные ограничения. Проверка источников не должна незаметно переписывать урок. / Check links, claims, and licensing for each finished lesson. Source monitoring must not silently rewrite a lesson. |
| P1 — последовательность | Строить темы от необходимых основ к продвинутым и научным уровням; переходить дальше по подтверждённому пониманию, а не по факту открытия страницы. | Sequence topics from prerequisites through advanced and, when appropriate, scientific levels. Advance based on demonstrated understanding, not merely opening a page. | Для курса видны предпосылки, текущий этап и следующий шаг. ## Рекомендуемый цикл занятия / Recommended lesson loop

**RU:** Диагностика → короткая цель → объяснение подходящей глубины → визуальное исследование → пример → самостоятельная практика → усложнение по результату → разбор ошибки → проверка переноса в новую задачу → фиксация выполненного → следующий шаг или повторение. Порядок меняется под предмет и состояние ученика, это не обязательный одинаковый шаблон.

**EN:** Diagnosis → a short goal → level-appropriate explanation → visual exploration → example → independent practice → result-based challenge → error analysis → transfer to a new task → record what was completed → next step or review. Adapt the order to the subject and learner; do not apply one rigid template.

## Ограничения и честная готовность / Limits and honest readiness

- **RU:** Индекс RAG и дата проверки источника не гарантируют, что текст урока автоматически обновился. Любое обновление содержания требует проверки редактором и фиксации источника.
- **EN:** An RAG index and source-check date do not mean lesson text was automatically updated. Content changes require editorial review and a recorded source.
- **RU:** Локальный API, готовый провайдер и реально ответившая модель — три разных состояния. Интерфейс и диагностика должны различать их.
- **EN:** A local API, a configured provider, and a model that actually answered are three different states. The UI and diagnostics must distinguish them.
- **RU:** Кодовая проверка Swift-модели не заменяет Xcode-сборку; Xcode-сборка не заменяет ручную проверку навигации, отображения, клавиатуры и VoiceOver на Mac.
- **EN:** A Swift model check does not replace an Xcode build. An Xcode build does not replace hands-on Mac review of navigation, rendering, keyboard access, and VoiceOver.
- **RU:** Ранний прототип не следует называть готовым продуктом до прохождения обязательных P0/P1-критериев и проверки на целевой macOS.
- **EN:** Do not describe an early prototype as a finished product until mandatory P0/P1 criteria and target-macOS acceptance have passed.

## Интерфейс и честные состояния продукта / Interface and truthful product states

**RU:** Главный экран должен давать понятный вход в предметы, сохранять действие «Продолжить обучение», показывать прогресс завершения курса отдельно от уровня освоения знаний и предлагать следующий шаг с коротким объяснением. Если уровень освоения ещё не подтверждён достаточными заданиями, так и написать — не заменять его выдуманным процентом знаний.

**EN:** The home screen should provide clear access to subjects, preserve the “Continue learning” action, show course-completion progress separately from knowledge mastery, and recommend the next step with a short reason. If mastery has not been established through enough evidence, say so instead of showing an invented knowledge percentage.

**RU:** Переходы проверять целиком: предмет → карта тем → урок → упражнение/визуализация → обратная связь → сохранённый прогресс → следующий шаг. Проверить все встроенные предметы и пользовательские темы; если ресурс действительно отсутствует, показать понятное восстановимое состояние с названием предмета и доступным действием.

**EN:** Check complete routes: subject → topic map → lesson → exercise or visualization → feedback → saved progress → next step. Cover every built-in subject and learner-created topic; if a resource is genuinely missing, show a useful recoverable state naming the subject and available next action.

**RU:** В настройках раздельно показывать доступность локального backend, Ollama, установленной модели, выбранного маршрута и фактического ответа модели. Одно зелёное состояние не должно скрывать, что следующий уровень подключения не проверен. Любой новый учебный блок (симуляция, 3D, видео, RAG-источник или AI-инструмент) получает отдельные статусы готовности и ограничения.

**EN:** Settings should report the local backend, Ollama, installed model, selected route, and an actual model reply as separate availability states. A green status must not hide that the next connection layer is unverified. Every new learning block (simulation, 3D, video, RAG source, or AI tool) needs its own readiness state and limitations.

## Диагностика реального ответа тьютора / Real tutor reply diagnostic

**RU:** В настройках добавляется отдельная проверка реального ответа по выбранному режиму «Авто» или «Только локально». Она отправляет короткий статический запрос через тот же `/chat/stream`, которым пользуется тьютор, и показывает провайдера, модель, длительность, фактический текст ответа или ошибку. Новый флаг `skip_retrieval` выключает поиск по материалам курса, заметкам Obsidian и официальным источникам для этой проверки; веб-поиск также отключён. Успех фиксируется только после непустого ответа. Проверка может расходовать лимит активного провайдера; платные маршруты по-прежнему ограничены отдельной настройкой расходов. Код и backend-тест добавлены, но реальный ответ на Mac ещё нужно проверить кнопкой в настройках.

**EN:** Settings add a real-reply check for the selected Auto or Local only mode. It sends a short static request through the same `/chat/stream` endpoint used by the tutor, then displays the provider, model, duration, actual answer text, or error. The new `skip_retrieval` flag disables retrieval from course materials, Obsidian notes, and official sources for this check; web search is also disabled. The check is successful only after a non-empty reply. It may use the active provider's quota; paid routes remain controlled by the separate cost setting. The code and backend regression test are in place, but a real Mac response still needs to be checked with the settings button.
