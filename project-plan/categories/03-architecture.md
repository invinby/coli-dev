# 03. macOS-архитектура

## Подтверждённое требование

Целевой продукт — полноценная платформа для macOS с онлайн- и офлайн-режимами. Пользователь просит аккуратный интерфейс, организованный с учётом принципов Apple.

## Текущее состояние

Текущий репозиторий содержит Python/FastAPI-оркестратор и прежний веб-интерфейс. SwiftUI-клиент в macOS/ColiDev содержит каталог шести направлений и обращается к /health, /chat/stream и локальному API ключей. В UI есть автоматический и локальный режимы; доступность маршрутов считается по облачному соединению, лимиту сессий и готовности Ollama. Retrieval использует подключённый Obsidian vault и отдельный офлайн-индекс курсов с лексическим поиском и опциональной локальной семантикой через Ollama. В настройках можно вводить ключи Gemini, Kimi и Obsidian; backend сохраняет их через macOS Keychain, показывает только статус/источник и сохраняет .env как dev-fallback. `/health` сообщает имя настроенной локальной embedding-модели без секрета, а SwiftUI показывает, включена ли такая настройка; это не проверка фактической доступности модели. Ключевые API-маршруты доступны только с loopback и отклоняют посторонний Origin. Local-only использует отдельный HTTP-клиент без системных proxy и разрешает Ollama только на loopback; Obsidian REST тоже ограничен loopback. UI блокирует неподтверждённые адреса. Шесть bilingual Markdown-карт включены в Resources-folder `02_Areas` внутри macOS app bundle; SwiftUI разбирает базовый, промежуточный и продвинутый уровни, показывает цели модулей и ведёт к текущему стартовому уроку. CI workflow проверяет сборку приложения и наличие каждого curriculum-файла внутри app bundle. Commit `ddd87c5` прошёл GitHub Actions run 37242014526: backend checks, macOS build и bundle-check успешны. Семантика проверена mock-тестами, но не реальным Ollama; UI пока не запускался на пользовательском Mac. Пользовательский Keychain и живой grounding тоже остаются непроверенными. Полный web-RAG пока не реализован.

## Первый реализуемый срез

SwiftUI-клиент читает встроенный учебный каталог и сохраняет язык, маршрут AI и отметки прохождения через UserDefaults. Отдельный клиент обращается только к localhost API: проверяет состояние, передаёт язык и режим, добавляет контекст урока и диалог, затем отображает SSE-ответ. Экран настроек принимает ключи через SecureField; локальный backend записывает их в macOS Keychain и никогда не возвращает значение в UI. `.env` остаётся dev-fallback, а статусы Keychain и переменных окружения не раскрывают сами ключи. Следующий шаг — подтвердить свежую macOS-сборку и продолжить проверку онлайн/локальных сценариев.

## Предварительное архитектурное предложение

Рассмотреть нативный SwiftUI-клиент для macOS, общий учебный доменный слой, локальное хранилище курсов/прогресса/индекса и отдельный слой AI-провайдеров. Существующий FastAPI-код оценить на повторное использование; не переписывать его и не переносить в приложение без аудита.

## Блоки целевого продукта

- Интерфейс macOS: каталог, учебный экран, практика, ИИ-тьютор, визуальная лаборатория, библиотека источников и настройки.
- Учебное ядро: курсы, уроки, задания, прогресс, повторение и профиль.
- Локальный слой: кэш курсов, индекс RAG, пользовательские данные и модели, если устройство справляется.
- Онлайн-службы: поиск/обновление источников, облачные модели и резервные провайдеры.
- Интеграционный слой: Obsidian и проверенный способ взаимодействия с NotebookLM.
- Визуальная лаборатория: схемы, симуляции и 3D только там, где это улучшает понимание.

## Apple-style интерфейс

Использовать нативные паттерны macOS, логичную иерархию навигации, системную типографику и компоненты, ясные состояния загрузки/ошибки/офлайна, доступность клавиатуры и VoiceOver, сдержанную анимацию и адаптацию под разные размеры окон. Проверить конкретные детали по актуальным официальным Apple Human Interface Guidelines перед разработкой.

## Архитектурные решения, которые ещё не утверждены

- SwiftUI выбран для первого нативного клиента. В Xcode-проекте пока стоит macOS 13 как прототипная цель; минимальную версию релиза нужно подтвердить.
- Какие части остаются в Python/FastAPI и как клиент с ними общается.
- Формат локального хранения и шифрование личных данных.
- Синхронизация между устройствами, если она понадобится.
- 3D-стек и требования к GPU/памяти.
